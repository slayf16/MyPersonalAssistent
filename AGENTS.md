# MyPersonalAssistent — правила для кодового ассистента

Общайся с заказчиком по-русски. Эти инструкции действуют на весь проект.

## Начало каждой сессии

1. Прочитай `docs/INVARIANTS.md`, `docs/WORKFLOW.md` и `docs/OPEN-QUESTIONS.md`.
2. Найди задачу в `tasks/`, соответствующую запросу. Прочитай `state.json` и её артефакты. Не выбирай случайно задачу другого исполнителя.
3. Продолжи с сохранённого этапа. Для новой задачи создай отдельный каталог через `scripts/task.ps1`. Каталог `tasks/` хранится только локально и исключён из Git. На новом компьютере при отсутствии локальных задач создай их заново по текущему запросу и состоянию проекта; не выдумывай прежние отчёты и результаты. Не добавляй `tasks/` в Git принудительно.
4. Прочитай профиль текущей роли из `docs/agents/`. Не объявляй независимое ревью, если его выполнял автор изменений.
5. Перед завершением сессии сохрани актуальные результаты, блокеры и следующий шаг в `handoff.md` задачи.

## Обязательные инварианты

Название приложения: `MyPersonalAssistent`. Android applicationId и namespace:
`com.mypersonalassistent`. minSdk: 26. MVP: текстовый чат, проверка на DeepSeek API.

Kotlin; Jetpack Compose; Material Design 3; Coroutines/Flow; Koin DI;
Decompose navigation/lifecycle; MVIKotlin MVI UI; Room DB; Ktor network; JUnit tests.
Многомодульность: `feature:<name>:api/impl` и `core:<name>:api/impl`.
`app` — точка сборки зависимостей. Не заменяй стек без явного решения заказчика.
Подробные ограничения и границы зависимостей — `docs/INVARIANTS.md`.

Внешний код/библиотеки допускаются только из открытых GitHub-репозиториев с >=30 звёздами.
До добавления проверяй актуальное число звёзд и лицензию, записывай доказательства
в `docs/DEPENDENCIES.md`. Не считай обязательный стек автоматически проверенным.
Правило относится к прямым зависимостям и заимствованным реализациям; транзитивные проверять не нужно.
Если проверить невозможно — зафиксируй блокер для этой зависимости.

## Процесс

Каждая задача проходит ANALYSIS → PLANNING → CODING → INVARIANT_VALIDATION →
CODE_REVIEW → TESTING → DONE. Правила переходов в `docs/WORKFLOW.md`.
Скрипт `scripts/task.ps1` фиксирует переходы и требует артефакты; он не проверяет
семантическую корректность отчётов. Не заполняй отчёты фиктивными результатами.
Интервью нужно при реальной неопределённости: уже полученные ответы не спрашивай повторно.
После PLANNING покажи заказчику конкретный план и дождись его явного аппрува.
До аппрува не запускай кодинг или кодеров. Изменённый план требует нового аппрува.
Сохрани цитату решения заказчика и дату/ссылку на сообщение; не выдавай исходную
постановку задачи или молчание за аппрув ещё не представленного плана.
На задачу разрешено максимум 2 цикла CODING → INVARIANT_VALIDATION → CODE_REVIEW → TESTING.
Первый вход в CODING — цикл 1; повторный вход для исправлений — следующий цикл,
даже если предыдущая попытка остановилась на ревью или проверке инвариантов.
Если лимит исчерпан и нужны исправления, остановись и попроси решение заказчика:
разрешить дополнительные циклы (с числом), исправить самому либо принять результат
с перечисленными проблемами и отдельно поручить коммит. Не начинай третий цикл сам.
Смена сессии, возврат в анализ и новая формальная задача не обнуляют лимит той же работы.
Ручные исправления заказчика проверяй заново; не исправляй их автоматически сверх лимита.
Принятие проблем не превращает FAIL/BLOCKED в PASS: используй ACCEPTED_WITH_ISSUES.
Изменения требований возвращают задачу в ANALYSIS; дефекты — в CODING в пределах лимита.

## Модели сабагентов

При запуске сабагента явно задавай модель и уровень рассуждений; наследование
модели родителя запрещено для этих ролей:

| Роль | Профиль | model | reasoning_effort |
|---|---|---|---|
| Кодер | docs/agents/android-developer.md | gpt-5.6-terra | high |
| Тестировщик | docs/agents/mobile-qa.md | gpt-5.6-terra | high |
| Аналитик | docs/agents/system-analyst.md | gpt-5.6-sol | medium |
| Код-ревьюер | docs/agents/code-reviewer.md | gpt-5.6-sol | medium |

Для `collaboration.spawn_agent` используй `fork_turns="none"` и передавай
в задании путь проекта, профиль, ID задачи, границы подзадачи и нужные артефакты.
Полный fork наследует модель, поэтому для этих ролей не подходит.
При другом механизме запуска укажи эквивалентные параметры явно.
Если требуемая модель недоступна, сообщи об этом; не подменяй её молча.
Эти правила определяют параметры запуска, но сами не запускают сабагентов.
Кодер и код-ревьюер — разные роли: проверка кода использует Sol medium.

## Code Review Rules

Проверяй границы api/impl, MVI, lifecycle/cancellation, конкурентные отправки,
стриминг/частичные ответы, повтор запросов и дубли сообщений, миграции Room,
утечки API-ключей и пользовательских сообщений, доступность Compose UI.
Каждый дефект: серьёзность, файл/строка, воспроизведение и ожидаемое поведение.
Не выдавай непройденные или незапущенные проверки за успешные.
